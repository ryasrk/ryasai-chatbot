# ADR 0013: A Parsed SQL Guard, and One Text-to-SQL Pipeline for Both Transports

**Status:** Accepted
**Date:** 2026-10-04
**Amends:** ADR 0002 (whose "AST" guard was a lexical scan)

## Context

ADR 0002 described the SQL guardrail as AST validation. The code was a hand-rolled token scan, and its own header
said so ("NOT a real SQL parser"). A scan rejects words; it cannot say which tables and columns a query reads, so it
could not support per-role data access, and every evasion needed another regex. Measured on 2026-10-04, two queries
passed the scan: a quoted function name (`SELECT "pg_read_file"('/etc/passwd')`) and a system catalog inside a quoted
comma-join (`FROM orders o, "pg_stat_activity" s`). Postgres `READ ONLY` stops neither — both are reads.

Separately, the Text-to-SQL branch was written twice: `runSqlBranch` (non-streaming: `/api/v1`, scheduler, agentic
loop) and `prepareSqlStream` (streaming: the web chat). The streaming copy — the one users reach — wrote no
`GUARDRAIL_BLOCK` / `SQL_EXECUTE` audit rows and no `queryHistory`, and skipped the SQL rate limit, `withToolSandbox`,
the integration `contextPrompt` and `textColumns`. The repo had recorded this drift class several times.

## Decision

1. **`sql-ast-guard.ts` parses with `node-sql-parser`** (PostgreSQL, MySQL/MariaDB, MSSQL) AFTER the lexical scan:
   exactly one `SELECT`, no `SELECT … INTO`, functions checked as nodes, system catalogs denied (including unprefixed
   `pg_*`), base tables/columns extracted for policy. **Fail-closed**: an unparseable query is rejected into the repair
   loop. ClickHouse is unsupported by the parser and stays lexical + server `readonly=1`.
2. The validated **text** runs, with the existing lexical LIMIT clamp — the tree is never re-serialised, so validation
   cannot change a query's meaning.
3. The AST runs when `{ provider }` is passed; every production caller passes it (`invariants.test.ts`). The
   provider-less call remains a unit-test seam for the scan.
4. The function deny-list moves to `sql-function-denylist.ts` so both layers share one copy.
5. **`pipelines/sql-pipeline.ts` (`runSqlPipeline`)** owns integration selection, rate limit, prompt inputs, repair
   loop, guard, execution and every audit/history row. The two transports only shape output.
   `transport-parity.test.ts` drives one scripted turn through both and requires identical side effects.

## Consequences

- Measured before adoption: 137 of 138 distinct real LLM-generated queries and 480 of 480 benchmark gold queries pass
  the full guard. The one miss (a CTE with a column list over `VALUES`) is regenerated by the repair loop.
- The web chat now has the SQL tool rate limit (default 10 SQL turns per minute per org, `checkToolRateLimit`) that
  only the non-streaming path had. Raise it if interactive use needs more.
- New SQL behaviour goes in the pipeline; an adapter that adds its own is the drift this ADR removes.
