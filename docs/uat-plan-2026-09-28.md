## Why local, not production

Production runs the same code, but UAT on it was rejected for three measured reasons:

| reason | measurement |
|---|---|
| LLM key belongs to the CUSTOMER | `LlmConfig`: `cbcn/deepseek-v4-flash`, `cbcn/deepseek-v4.1-flash`, key present |
| credentials unavailable | `.env` has `admin@ryasai.local`, DB has `demo@demo.com`, login → **401** |
| insufficient data | 0 integrations, 1 document — SQL/chart/multi-source flows untestable |

Local has the ingredients production lacks: **3 connected PostgreSQL integrations**, **10 Indonesian policy
documents** (56 chunks), **4 API keys**, **5 plugins**, **1 MCP server**, **1 schedule**, and a working login.

## The 10 personas

Each is a role that exists in a real on-prem deployment. A persona is not a feature list — it is the
sequence and vocabulary a real person would use, including their wrong turns.

| # | persona | mission | why this persona exists |
|---|---|---|---|
| 1 | **First-run admin** | Setup wizard, AI config, first document, first question | The highest-drop-off path; a new customer sees only this |
| 2 | **RBAC admin** | Invite users, assign roles, verify what each role can see | Multi-tenancy is load-bearing; role leakage is a security defect |
| 3 | **Sales analyst (SQL)** | 12 business questions against Sales DB in Bahasa Indonesia | The product's core promise: NL → SQL on real data |
| 4 | **Cross-source analyst** | Questions spanning HR + Sales + Logistics; ambiguous questions | Multi-step DAG and disambiguation were recently rewired |
| 5 | **Knowledge officer (RAG)** | Ask the 10 policies; check citations and refusal honesty | RAG is described as the strongest subsystem — verify or refute |
| 6 | **Power user (UX)** | Long sessions, rename, delete, history, markdown, charts, mobile | Session state was the source of two recent user-reported bugs |
| 7 | **Integrator (API)** | Create API keys, call `/v1/chat/completions`, probe scoping | The whole scope axis was just fixed; test it as an attacker would |
| 8 | **Operator (settings)** | Prompt tools, schedules, notifications, plugins, MCP | Config surfaces where a wrong toggle silently disables a feature |
| 9 | **Adversarial user** | Empty/huge input, injection, unicode, XSS, SQLi, concurrency | Real users and real attackers both do this |
| 10 | **Accessibility user** | Keyboard-only, contrast, ARIA, zoom, screen-reader labels | An on-prem customer with a procurement checklist asks for this |

## Constraints given to every agent

- **LOCAL ONLY.** Never contact `172.30.2.74` / `ryasai.my.id`.
- **LLM budget**: ≤15 provider calls per agent. Prompts are paid for by the customer's key.
- **May create and delete TEST data freely** (own documents, sessions, API keys, schedules).
- **May not** drop schemas, truncate tables, or delete the seeded integrations/documents.
- **Report what WORKS**, not only what fails — a UAT that only lists bugs is not evidence of quality.
- **Evidence or it did not happen**: every finding needs the command and its output.

## Report format required from each agent

```
persona, duration_estimate
worked:    [things verified as functioning, with evidence]
findings:  [ {severity: blocker|major|minor|nit, title, evidence, repro, expected, actual} ]
blocked:   [what could not be tested and why]
coverage:  [surfaces touched vs skipped]
```

Severity bar:
- **blocker** — a real user cannot complete the persona's core job
- **major** — wrong result, data leak, or silent failure
- **minor** — works but confusing/slow/inconsistent
- **nit** — cosmetic

## After the agents return

1. **Deduplicate** findings across personas (the same defect seen by 4 agents is one defect).
2. **Verify each blocker/major myself** before reporting it — an agent's claim is a lead, not a fact.
3. **Fix what is cheap and unambiguous**; report the rest with severity.
4. **Production smoke test** (read-only): health, public page, auth rejection, one real question.
5. **Clean up** test data created by the agents.
